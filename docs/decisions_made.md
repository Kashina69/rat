# Decisions made — Realtime Ammo Tracking (RAT) POC

Log only: decision, choice, why, consequence. Behaviour today and open gaps live
on @docs/project-status.md. The original spec and the phase plans are in git
history, not truth.

| # | Decision | Choice | Why | Consequence |
|---|---|---|---|---|
| 1 | Product scope | POC for one depot covering the 12 capabilities in @docs/00-product-scope.md | Prove the gate→shed→gate loop in a real depot on cheap tablets, not an ERP project | Offline mutations, refresh tokens, Redis/multi-instance, native app, self-signup and multi-depot stay out |
| 2 | Database | **MySQL 8.4** + Prisma 6 in Docker, a deliberate deviation from the concept's PostgreSQL | Depot-side ops know MySQL; it is what the demo host runs (user decision 2026-10-30) | No Postgres-only features; row locking via `SELECT … FOR UPDATE` in `server/src/utils/rowLocks.ts`. The concept's Postgres reasoning is void, not pending |
| 3 | Status vocabulary | Visit `AWAITING_LOADING` → `PARTIALLY_LOADED` → `READY_FOR_CHECKOUT` → `CHECKED_OUT` + `CANCELLED`; line `PENDING` → `LOADED` + `CANCELLED` | One vocabulary across DB, API, filters and screens | These strings are the contract; the old names (Registered, Partly loaded, Loaded) are bugs anywhere they appear |
| 4 | Short stock at the gate | **Warn only** — the gate sees a warning and can still save | The shed shelf is the truth; stale records must not block the gate | No 409, no clamp. The "saved with low stock" toast is informational and must never become a validation error |
| 5 | Stock at shed confirm | No on-hand block: recorded stock **may go negative**. `loadedQty` must be 1..requested. Double confirm → `409 ALREADY_CONFIRMED`, no state change | Partial or over-recorded stock happens; blocking the storekeeper strands the vehicle. The ledger carries correctness | `currentStock` and `balanceAfter` can legitimately be negative and must be shown, not hidden; stock cannot be double-deducted |
| 6 | Item editing | Name, category, reorder level editable any time; unit and shed fixed at creation; stock moves only through stock-in, adjust or confirm; archive instead of hard delete | Renames are routine; changing unit/shed would rewrite history; deleting would orphan ledger rows | `PUT /api/items/:id` accepts name, category, reorderLevel, isActive only; every stock change writes exactly one ledger row |
| 7 | Users | Four seeded logins (`admin`, `gate`, `sheda`, `shedb`); admin creates users, sets role + shed, disables/enables, resets passwords. No self-signup | A handful of named staff; show provisioning without building an identity system | Disabled login → generic 401; disabled token → `403 ACCOUNT_DISABLED`; self-disable blocked. No last-admin guard |
| 8 | Export | CSV **and** Excel (`.xlsx`) with the same filters as the log screen | CSV for scripts, Excel for reports | Both built on one query path and must stay in step |
| 9 | Auth and session | JWT access token only (~8 h), bcrypt 12 rounds, token in React memory, never `localStorage`; no refresh token, no revocation list; role + shed code in the payload | One shift, shared tablets, physically controlled; revocation infrastructure is out of scope | Cold launch = fresh login; logout must clear in-memory auth **and** the query cache or the next user sees cached data; a leaked token lives until expiry |
| 10 | Realtime | Socket.IO rooms `shed:{code}`, `gate`, `admin`; events are invalidation hints, never state | One source of truth (REST + DB); survives missed events and reconnects | Write the DB first, then emit; clients refetch on event, reconnect and refocus. A dead socket degrades to stale-until-refetch |
| 11 | Logs and dashboard | Log filtered by vehicle, item, shed, line status and `from`/`to`, paginated, exported with the same filters. Dashboard: vehicles inside, pending lines per shed, low stock | That is what the office asks for at the counter | Date filters are depot-local (IST) days, so `to=today` includes today. "Low stock" is `currentStock <= reorderLevel`; a full per-shed current-stock list is not built |
| 12 | Deploy | Docker Compose: `mysql:8.4`, `api`, `web`, a dev file, and a self-contained `docker-compose.prod.yml`; HTTPS in front for PWA install | One repo, one command, reproducible demo host | Prod API refuses to boot without `JWT_SECRET` (≥32) and `CORS_ORIGIN`; seeding needs all four `SEED_*_PASSWORD` values; `NEXT_PUBLIC_*` are build args, not runtime env |
| 13 | Demo | Seeded depot (2 sheds, ~10 items, 4 logins) plus a scripted 3–5 vehicle run including a multi-shed and an over-stock vehicle, from installed tablets | The demo is the acceptance test for the POC | Demo claims only count once the run happened — it has not |
| 14 | Quality | Express 5 + TypeScript strict, `route → controller → service → Prisma`, zod at every input boundary, `{ data }` / `{ error: { code, message } }`, no classes, append-only ledger, server-side shed scoping, Vitest + Supertest on a real `rat_test`, Biome + `tsc --noEmit` | Small POC, high blast radius on stock numbers: invariants beat abstraction | Client role checks are UX only, never security. `SUM(ledger.delta) == item.currentStock` is a test-enforced invariant. `truncateAll` refuses any DB not ending `_test`. No CI |
| 15 | Documentation | @docs/decisions_made.md + @docs/project-status.md are the authoritative pair; spec and phase plans are history | Docs had drifted badly (old status chain, fields that never existed) | Behaviour changes update this file or the status file in the same change |
